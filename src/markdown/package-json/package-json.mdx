Dans chacun de nos projets se trouve **ce fichier familier que l'on ouvre qu'en de rares occasions** avant de le refermer aussitôt : _el famoso_ `package.json`.

Et c'est fort dommage, car cet incontournable des stacks web **recèle quelques secrets et des pouvoirs insoupçonnés** par la plupart des devs.

Faisons un point sur toutes les possibilités qu'offre le `package.json` pour doper votre workflow !

## Les commandes personnalisées

Balayons un fait assez connu : la section `scripts` permet de créer des alias tels que `dev`, `build`, `typecheck`, `test` servant de raccourci pour exécuter **des commandes récurrentes dans notre projet**.

```json
{
  "scripts": {
    "dev": "vite",
    "lint": "biome check ."
  }
}
```

<InformationBanner status="info">
Vous êtes-vous déjà demandé comment ces alias pouvait invoquer des librairies comme `vite` ou `next` que vous n'avez pourtant pas installées globalement ? Car **avant d'exécuter votre commande, votre gestionnaire de paquets ajoute temporairement le** `node_modules/.bin` de votre projet au `PATH` de votre session afin d'accéder à toutes ses dépendances.
<br/>
Taper `vite` échouera probablement mais dans un script cela fonctionne car notre package manager se réfèrera à l'exécutable installé localement dans le projet et défini par votre lockfile.
<br/>
L'avantage immédiat est que vos scripts sont reproductibles d'une machine à l'autre : **tout le monde exécute ainsi la même version du même outil** lors du lancement du script. Pas de risque par exemple qu'un `typescript` 7 installé globalement sur votre machine tourne lors d'un typecheck quand votre collègue utiliserait de son côté un `typescript` 6. Seules font foi les **dépendances explicitement listées dans votre `package.json`**.
</InformationBanner>

Plus méconnus sont en revanche les hooks `pre` et `post` qui ajoutent encore plus de flexibilité à ces commandes.

Qu'est-ce donc ? Lorsque vous lancez un script `build`, par exemple, npm va **spontanément chercher deux autres scripts** : `prebuild` et `postbuild`. S'ils existent, `prebuild` sera exécuté avant `build` et `postbuild` juste après.

```json
{
  "scripts": {
    "prebuild": "rimraf dist", /* le dossier dist est supprimé */
    "build": "vite build", /* le site est compilé */
    "postbuild": "node tools/report-size.js" /* la taille du bundle est affichée */
  }
}
```

Cette convention vaut pour **n'importe quel nom de script** (on peut ainsi avoir des `pretest`, `postdeploy`, `prerelease`…) et permet d'attacher proprement des étapes de préparation ou de nettoyage autour d'une commande sans bourrer celle-ci de `&&` et perdre en lisibilité.

Une façon bien plus propre d'écrire et de séparer les responsabilités au sein de vos scripts !

<InformationBanner status="warning">
Ce comportement automatique est **une spécificité de npm** : <LinkWithGlimpse url="https://pnpm.io/settings#enableprepostscripts">pnpm ne les exécute pas par défaut</LinkWithGlimpse> et exige un `enable-pre-post-scripts=true` explicite, tandis que <LinkWithGlimpse url="https://yarnpkg.com/advanced/lifecycle-scripts">Yarn Berry a purement et simplement refusé de les supporter</LinkWithGlimpse>. Derrière cette limitation se trouve une motivation raisonnable : **ces étapes implicites peuvent aussi obscurcir le flux d'exécution** : un nouvel arrivant sur un projet qui lit `"build": "vite build"` n'a aucun moyen de deviner que d'autres commandes s'exécutent autour.
</InformationBanner>

## D'autres scripts cachés encore...

Il existe une seconde famille de scripts, autrement plus dangereuse : **les scripts de cycle de vie que npm va déclencher tout seul à l'installation d'une dépendance**. `preinstall`, `install` et `postinstall` s'exécutent en effet non seulement pour votre projet, mais **pour chacune des dépendances que vous installez**.

<Image width={500} src={ISeeDeadScriptsImage} alt="A child saying 'I see dead scripts'" className="mx-auto my-12 w-150 max-w-full"/>

Historiquement il s'agissait de permettre à certaines librairies de **compiler des modules natifs** ou de **télécharger un binaire utile à leur bon fonctionnement**.

Mais cette facilité permet également à des librairies malveillantes **exécuter du code arbitraire sur votre machine à chaque `npm install`** ce qui en a fait le vecteur privilégié d'une série d'attaques de la chaîne d'approvisionnement (_supply chain attacks_) <LinkWithGlimpse url="https://securitylabs.datadoghq.com/articles/shai-hulud-2.0-npm-worm/">dans l'écosystème npm ces dernières années</LinkWithGlimpse>.

Conscient du problème et imitant en cela pnpm, Yarn et Bun qui bloquaient déjà ces scripts, **npm v12 désactive dorénavant leur exécution par défaut**.

Les paquets ayant réellement besoin de ces scripts pre ou post installation doivent désormais être **explicitement autorisés** avec la commande suivante :

```bash
npm approve-scripts --allow-scripts-pending
```

## Passer des arguments et lire l'environnement

Un script n'est pas toujours une commande figée et peut parfaitement recevoir des arguments pour en modifier le comportement. Par exemple, tout ce qui est placé après un double dash `--` est **transmis tel quel à la commande qui le précède** :

```bash
npm run test -- --watch
npm run build -- --mode staging
```

Vos scripts peuvent également accéder à **des variables d'environnement** à commencer par les champs du `package.json` lui-même :

```json
{
  "version": "2.4.0",
  "scripts": {
    "release": "echo \"Publication de la version $npm_package_version\""
  }
}
```

Pratique pour tagger une image Docker ou nommer une archive sans jamais dupliquer le numéro de version !

<InformationBanner status="warning">
Attention en revanche à la définition de variables : la syntaxe `MA_VAR=valeur ma-commande` **fonctionne sur macOS et Linux, et échoue sur Windows**. C'est là qu'intervient un utilitaire comme <LinkWithGlimpse url="https://github.com/kentcdodds/cross-env">`cross-env`</LinkWithGlimpse> avec une syntaxe unique fonctionnant pour toutes les plateformes :

```json
{
  "scripts": {
    "build:staging": "cross-env NODE_ENV=production API_URL=https://staging.api vite build"
  }
}
```
</InformationBanner>

## Orchestrer plusieurs tâches parallèlement

Les projets réels enchaînent rarement une seule action. Le shell offre déjà deux opérateurs pour les articuler, le `&`et le `&&` :

```json
{
  "scripts": {
    "ci": "npm run lint && npm run test && npm run build",
    "dev": "npm run dev:css & npm run dev:server"
  }
}
```

Le `&&` **enchaîne les commandes en séquence** qui s'interrompt totalement si l'une des étapes échoue. Le `&` simple **les lance en parallèle**…


<InformationBanner status="warning">
Le `&` présente la même limite que celle vue précédemment pour les variables d'environnement personnalisées : **il n'existe pas vraiment sous Windows qui lui donne une autre signification** \*_windows fatigue intensifies_\*.
<Image width={500} src={WindowsLinuxMacos} alt="Three dragon heads, two labeled MacOS and Linux, and the third stupid Windows" className="mx-auto my-8 w-150 max-w-full"/>

Pour du parallélisme fiable entre toutes les plateformes, deux outils dédiés ont fait leurs preuves : <LinkWithGlimpse url="https://github.com/bcomnes/npm-run-all2">`npm-run-all2`</LinkWithGlimpse> (le fork maintenu de l'historique `npm-run-all`) et <LinkWithGlimpse url="https://github.com/open-cli-tools/concurrently">`concurrently`</LinkWithGlimpse> :

```json
{
  "scripts": {
    "dev:css": "tailwindcss -i src/app.css -o dist/app.css --watch",
    "dev:js": "vite",
    "dev:api": "node server.js",
    "dev": "run-p dev:*"
  }
}
```

`run-p` pour *parallel*, `run-s` pour *sequential*, et un `dev:*` qui ramasse automatiquement tous les scripts partageant le même préfixe.
</InformationBanner>


## Exécuter du javascript avec une commande

Les alias de commande peuvent vite devenir limités dès que vous avez besoin d'une condition (« supprimer ce dossier *seulement s'il existe* »), d'une boucle ou d'une gestion d'erreur. Non seulement **la commande en une ligne devient un enfer illisible** mais elle peut ne pas fonctionner à l'identique d'un système d'exploitation à l'autre.

Dans ce cas, il est préférable de **faire pointer votre alias vers un vrai fichier JavaScript contenant toute la logique d'exécution**.

```json
{
  "scripts": {
    "release": "node tools/release.js",
    "generate:icons": "node tools/generate-icons.js"
  }
}
```

J'utilise par exemple souvent un script personnalisé de lint qui vient toiletter mes fichiers de traduction en les réordonnant, vérifier que chaque fichier de langue est exhaustif et qui repère les clefs de traduction mortes lorsque la librairie que j'utilise n'offre pas de telles fonctionnalités.

## Ajouter sa propre CLI

Et là on rentre carrément dans les arcanes du `package.json` là où peu s'aventurent. Avec un champ `bin`, vous pouvez **associer un nom de commande à un fichier exécutable**.

```json
{
  "name": "@monprojet/tooling",
  "bin": {
    "exec": "./tools/cli.js"
  }
}
```

Le fichier ciblé doit commencer par un *shebang* pour préciser le `runtime`.

```js
#!/usr/bin/env node

// tools/cli.js
const [command, ...args] = process.argv.slice(2);
// ...
```

Une fois le lien établi, la commande devient disponible **comme n'importe quel outil installé** :

```bash
exec new component Button
# ✨ src/components/button/button.tsx créé
```

C'est de cette manière que Vite, Angular, ESLint ou Prisma mettent à disposition leur propre CLI sans nécessiter un `npm run`.

**Rien ne vous empêche donc d'en faire autant** : vos collègues récupèreront les mêmes commandes sans rien devoir installer de plus. Votre codebase peut inclure **sa propre CLI** pour uniformiser le workflow entre ses contributeurs.

## Les champs oubliés

La section `scripts` monopolise l'attention, mais quelques autres champs méritent largement le détour :

- **`imports`** définit des alias d'import **résolus nativement par Node**, sans configuration de bundler ni de TypeScript. Les clés doivent commencer par `#` :

```json
{
  "imports": {
    "#utils/*": "./src/utils/*.js"
  }
}
```

- **`engines`** et **`packageManager`** verrouillent respectivement la version de Node et celle du gestionnaire de paquets attendues par le projet. De quoi **mettre fin aux écarts de version entre deux machines** qui donnent des résultats différents.

```json
{
  "engines": {
    "node": ">=24"
  },
  "packageManager": "pnpm@10.15.0"
}
```

- **`overrides`** (ou son équivalent `resolutions` chez Yarn) force la version d'une dépendance transitive, ce qui reste **le seul moyen de corriger une faille de sécurité** dans un paquet que vous n'installez même pas directement.

```json
{
  "overrides": {
    "cross-spawn": "^7.0.5", /* partout dans l'arbre de dépendances */
    "vite": {
      "esbuild": "^0.25.0" /* uniquement lorsqu'il est requis par vite */
    }
  }
}
```

- **`files`** liste ce qui sera réellement embarqué lors d'une publication sur npm.

```json
{
  "files": [
    "dist",
    "!dist/**/*.test.js"
  ]
}
```

- **`workspaces`**, enfin, transforme votre dépôt en monorepo et fait le lien avec <LinkWithGlimpse url="https://www.frenchdev.co/post/monorepo-1" internalLink={true}>les avantages d'un monorepo</LinkWithGlimpse>.

```json
{
  "private": true,
  "workspaces": [
    "apps/*",
    "packages/*"
  ]
}
```

## Faut-il jeter les gros orchestrateurs pour autant ?

Il serait malhonnête de conclure que le `package.json` remplace tout. Sur un monorepo conséquent, **la mise en cache des tâches, leur parallélisation intelligente et l'exploitation du graphe de dépendances** — ce que font <LinkWithGlimpse url="https://turbo.build">Turborepo</LinkWithGlimpse> ou <LinkWithGlimpse url="https://nx.dev">Nx</LinkWithGlimpse> — restent hors de portée d'une section `scripts`, et le sont de plus en plus à mesure que le projet grossit.

Mais il faut reconnaître que **l'écrasante majorité des projets frontend n'en arrive jamais là**, et que la tentation est grande d'installer l'orchestrateur avant d'en avoir le besoin. Or **une dizaine de scripts bien nommés que vous comprenez intégralement vieilliront toujours mieux qu'un fichier de configuration que vous n'osez plus toucher**, dont la moitié des options ont été copiées d'un article de blog et dont une mise à jour surprise peut casser la CI du jour au lendemain.
